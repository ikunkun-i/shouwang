# 仓库搭建与协作规范

本文件写给《守望》项目组全体：仓库怎么建、队友怎么进、每天怎么提交、提交日怎么同步到 AtomGit。凡与本文冲突的做法，以本文为准。

## 零、环境说明

本机未安装 Git for Windows，PowerShell 里直接敲 `git` 会报“无法识别”。有两个选择：

- 用 GitHub Desktop 的全部图形操作（推荐，够用）。
- 想用命令行：GitHub Desktop 自带 git，路径为
  `C:\Users\lenovo\AppData\Local\GitHubDesktop\app-3.6.10\resources\app\git\cmd\git.exe`，
  在 PowerShell 里先设一次别名：

  ```powershell
  Set-Alias git "C:\Users\lenovo\AppData\Local\GitHubDesktop\app-3.6.10\resources\app\git\cmd\git.exe"
  ```

  或直接装 Git for Windows（自带 Git Bash 与 PATH 配置），队友按装 Git 更省事。

本文出现的 `git` 命令，均指在这两种环境下执行。

## 一、建库前的两个决定

1. 仓库设为 **Public**。比赛要求公开源码，公开仓库的协作者人数也不受限制；私有仓库免费版最多 3 个协作者，5–6 人的队伍会撞上限。
2. 仓库名用**纯英文**，避免 AtomGit 同步与命令行转义问题。建议 `shouwang`，备选 `osgj2026-shouwang`。

## 二、本地建库步骤（GitHub Desktop）

推荐先用本地已有目录建库，再发布，避免空仓库首次提交的坑。

1. 本地目录已按约定结构备好（见本项目根目录）。
2. GitHub Desktop → `File` → `Add existing repository`（若本地已有 `.git`）或 `File` → `New repository`（若尚未初始化），Name 填 `shouwang`，Local path 指向本目录。
3. 提交首次内容：Summary 写 `init: 项目骨架与规范文档`，点 `Commit to main`。
4. 点 `Publish repository`，**取消勾选 `Keep this code private`**。

首次提交前请确认 `.gitignore` 已生效：左下角 Changes 里不应出现 `.godot/`。若出现，先删除再跟踪：

```powershell
git rm -r --cached .godot
```

## 三、邀请队友（Collaborator 方案）

GitHub Desktop 没有成员管理入口，需在浏览器操作。

1. 打开 `https://github.com/ikunkun-i/shouwang/settings/access`。
2. 点 **Add people**，输入队友的 GitHub 用户名或邮箱，一次可加多人。
3. 权限**只给 Write**，不要给 Admin。合并权集中在队长手里。
4. 队友收到邮件邀请，点 Accept 后即可直接 clone 本仓库，**不需要 fork**。
5. 加完人后配置 `main` 分支保护，具体字段见 4.1，**批准数先填 0**，等人齐再改 1。
6. （可选）`Settings` → `General` → Danger Zone 里确认仓库为 Public。

**发给队友的邀请话术**：

> 仓库地址：https://github.com/ikunkun-i/shouwang
> 已把你加为协作者，邮件里点接受就能看到（找不到就看垃圾箱）。
> 本地流程：`git clone` → `git switch -c feat/p1-battle`（P2 用 `feat/p2-economy`，P3 用 `feat/p3-flow`）。
> 每天收工前 push 一次，合并走 PR 到 main，我来合。main 有保护，别直推。

**队友首次操作（Windows PowerShell）**：

```powershell
git clone https://github.com/ikunkun-i/shouwang.git
cd shouwang
git switch -c feat/p1-battle
```

用 GitHub Desktop 的话：`File` → `Clone repository` → 选 `shouwang` → `Branch` → `New branch` 填 `feat/p1-battle`。

## 四、分支、提交与标签约定

- 分支：`feat/p1-*`、`feat/p2-*`、`feat/p3-*`，缺陷修复用 `fix/*`，文档用 `docs/*`。
- 一个分支只做一件事，做完就发 PR，不要攒到第三天。
- 提交信息格式：`P1: 塔位合法性判定与建造扣费`（域前缀 + 做了什么）。
- 里程碑打标签：
  - `v0.1-d4`：D4 收工，能打完一关
  - `v0.2-d5`：D5 收工，跑通“胜利→商店→再胜”
  - `v1.0-submit`：提交版
- 禁止直接推 `main`；禁止强推（`--force`）；禁止把 `build/`、导出包、临时文件提交进仓库。

### 4.1 分支保护设置

保护规则只管“推送进 `main`”，不影响队友推自己的分支。仓库是 Public，这项功能免费。

**入口**

- 常规：仓库页右上 `Settings` → 左侧 `Code and automation` 下的 `Branches` → 右侧 `Add branch protection rule`（新版可能写作 `Add rule`）。
- 若找不到 `Branches`：`Settings` → `Rules` → `Rulesets` → `New branch ruleset`。两者等价，Rulesets 多一个“豁免名单”，见下。

**逐项填写**

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| Branch name pattern | `main` | 只保护主干，分支不受限 |
| Require a pull request before merging | 勾选 | 这条是核心，保证所有改动经 PR |
| ↳ Require approvals | 先 **0**，人齐后改 **1** | 见下方“自我批准的限制” |
| ↳ Dismiss stale pull request approvals when new commits are pushed | 勾选 | 批完又推新提交，旧批准作废，防止“批的和合的不是同一份代码” |
| ↳ Require conversation resolution before merging | 不勾 | 事务多时反而卡进度 |
| Require status checks to pass before merging | 不勾 | 还没有 CI，勾了会把所有 PR 锁死 |
| Require signed commits | 不勾 | 队员没有签名密钥，勾了全员被拦 |
| Require linear history | 不勾 | 会禁止 merge commit，Desktop 合并直接报错 |
| Lock branch | 不勾 | 勾了分支变只读，连 PR 也合不进去 |
| Do not allow bypassing the above settings | 先不勾 | 留一条队长紧急处置的口子，队伍稳定后再议 |
| Restrict who can push to matching branches | 空 | 不需要额外限定 |
| Allow force pushes / Allow deletions | 都不勾 | 强推与删分支一律禁止 |

填完点 `Create` 或 `Save changes`。

**必须知道的限制：作者不能批准自己的 PR**

GitHub 硬规则：PR 作者无法给自己批准。因此若只有队长一人有 Write 权限、批准数又设成 1，队长自己的 PR 会永远停在 “1 approval required”，合不进 `main`。两种解法：

- 先填 0，只要求“走 PR”；三位程序都进来、能互相批之后，再回来把 0 改成 1。**推荐**。
- 或在 Rulesets 里把自己的账号加进 Bypass list（豁免名单）；但那样规则对队长形同虚设，不如上一种干净。

**验证是否生效**

```powershell
git switch main
git commit --allow-empty -m "test: 验证分支保护"
git push origin main
```

预期被拒，报 `protected branch hook declined` 或 `GH006: Protected branch update failed`。验证完撤销这条空提交：

```powershell
git reset --hard HEAD~1
```

### 4.2 PR 流程（标准动作）

人员与分支的对应关系见 `docs/team.md`，一人一条分支，不要两人共用同名分支。

1. 建分支：GitHub Desktop → `Branch` → `New branch`，基于 `main`，命名见第四节。
2. 开发、`Commit`、`Push origin`。注意推的是**自己分支**，不是 `main`。
3. 网页仓库首页会出现 `Compare & pull request`，点它；标题写清域前缀，如 `P1: 航路与塔位判定`；说明里写“改了什么、怎么验、影响谁”。
4. 请另一位组员 `Files changed` → `Review changes` → `Approve`。
5. 批准数达标后点 `Merge pull request` → `Confirm merge`。
6. 回 GitHub Desktop：切回 `main`，`Fetch origin` → `Pull origin`，把合并结果拉下来再开下一个分支。

命令行等价物（装了 Git 或已设别名时）：

```powershell
git switch main
git pull
git switch -c feat/p1-battle
# 开发后
git add -A
git commit -m "P1: 航路与塔位判定"
git push -u origin feat/p1-battle
```

### 4.3 卡住了怎么自救

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| PR 显示 “Review required”，自己批不了 | 作者不能自我批准 | 让另一位组员批；或把批准数临时调回 0 |
| `git push` 报 `protected branch` / `GH006` | 保护生效，正在直推 main | 改推分支，再发 PR；不要 `--force` |
| Desktop 合并后本地历史落后 | 没拉取 | `Fetch origin` → `Pull origin` |
| 提示 `This branch is out-of-date with the base branch` | 分支落后于 main | 先 `git merge main` 解决冲突，再推 |
| 冲突提示 `CONFLICT (content)` | 两人改了同一文件 | 打开文件手工合并，删掉 `<<<<<<<`/`=======`/`>>>>>>>` 标记，再 `git add` 提交 |
| 找不到 `Branches` 设置页 | 新版 UI 已迁到 Rulesets | 走 `Settings` → `Rules` → `Rulesets` |

**D4、D5 联调期的调整**：这两天合并频繁、互相等批准容易卡进度，把 `Require approvals` 临时调回 0（仍要求走 PR），保证随时能合；D6 进入功能冻结后再调回 1。整个赛期保持 `Do not allow bypassing` 不勾，紧急情况下队长可在网页直接合并。

## 五、每日流程（三人一致）

1. 早上：`git switch main` → `git pull` → 切回自己分支 → `git merge main`，先吃掉别人的接口变更。
2. 开发：只动自己域内的文件；跨域需求发到群里，由负责人改。
3. 收工：`git add -A` → `git commit -m "P1: xxx"` → `git push`。
4. 每日收工由 P3 在合并后的分支上打包一次，全队在真机上运行当天版本；未运行视为未验收。

## 六、文件与素材规则

- 代码、场景、数据一律用 English 路径与文件名，避免跨平台与工具链问题。
- 图片、音频统一放 `assets/` 下对应子目录，并走 Git LFS（`.gitattributes` 已配置）；首次提交大文件时 GitHub Desktop 会提示启用 LFS，点同意。
- 第三方素材必须登记到 `docs/AI使用与素材声明.md`，写清来源、许可、是否改动。
- 策划案、分工方案等 PDF 放 `docs/`，不要散落在根目录。

## 七、AtomGit 同步（提交日前完成）

比赛以 AtomGit 仓库为准，GitHub 只作日常开发。本地仓库配两个远端：

```powershell
git remote add atomgit https://atomgit.com/<你的账号>/shouwang.git
git remote -v
```

日常只推 GitHub；提交日：

```powershell
git switch main
git pull
git tag v1.0-submit
git push origin main --tags
git push atomgit main --tags
```

注意事项：

- AtomGit 仓库必须包含**完整可运行源码**、`docs/AI使用与素材声明.md`，以及可运行发行版与启动说明（发行版可放 Release，不放仓库正文）。
- **不要在原子派内提交**，那边提交无效。
- 提交后版本锁定，赛期内不要再改 tag。
